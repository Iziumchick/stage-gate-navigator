## Граница решения

Проверка почты контролирует, кто получает аккаунт и доступ к API, но не закрывает
сам вебсервер от интернета. Домен сайта, суффикс email и сеть OTH — три разных
вещи. Наличие адреса @oth-regensburg.de не делает запрос пришедшим из Hochschulnetz.

По предоставленному письму возможны публичный доступ с требуемым независимым
аудитом либо сетевое ограничение; отдельно описывается возможность внешнего
хостинга с сохранением требований к конкретному сервису. Нельзя самостоятельно
считать внешнего провайдера, WAF или верификацию email заменой согласования и
аудита. Применимость и режим для этого проекта нужно уточнить у руководителя,
ITZ и Informationssicherheitsbeauftragter. Автоматические тесты разработчика
не являются независимым внешним аудитом.

не увидел принципиальной проблемы в собственной регистрации либо проверке

сервера или подтверждение соответствия опубликованной конфигурации. Требования
к возможной передаче факультету отдельно не согласованы.

## Что реализовано

- Для регистрации учебных аккаунтов допускаются ровно `st.oth-regensburg.de` и `oth-regensburg.de`; похожий суффикс,
  дополнительный поддомен и чужой домен не принимаются. Это не механизм
  назначения ролей: зарегистрированный сотрудник получает обычный личный доступ.
- По запросу оператора добавлено одно точное исключение: существующий аккаунт
  с ролью admin может входить через внешний адрес, совпадающий с `ADMIN_EMAIL`.
  Это не разрешает регистрацию Gmail/других внешних учебных аккаунтов. Внешний
  администратор также подтверждает почту кодом. Изменение `ADMIN_EMAIL` закрывает
  прежнее внешнее исключение; у других университетских администраторов доступ
  определяется их явно назначенной ролью и подтверждением почты.
- Для ограниченного режима после регистрации приходит шестизначный код на 10
  минут. Нужны и код, и случайный секрет текущего окна подтверждения. В БД
  сохраняются хеши; открытые коды/секреты не попадают в ответы API или логи.
- Новый аккаунт создаётся после подтверждения. До этого временно хранятся
  pending-регистрация с хешем пароля и согласие; неподтверждённый адрес нельзя
  заранее занять как действующий аккаунт. Просроченные записи удаляются при
  последующих запросах и ежедневной очистке.
- Максимум 5 ошибочных попыток для одного кода. Повторная отправка — не раньше
  60 секунд, максимум 5 отправок на адрес за час и 30 на приложение за минуту.
  Новый код отменяет предыдущий, успешное подтверждение одноразовое и атомарное.
- Старые аккаунты не считаются подтверждёнными автоматически. При включении
  режима старая сессия без подтверждения больше не даёт доступ к данным.
  После подтверждения вход осуществляется отдельным паролем приложения.
- В ограниченном режиме личные обзоры, прежние диагностические примеры и PDF
  каталога требуют входа. Сведения о конфиденциальности, вход и health доступны.
- Обновление 21.11.2026: по запросу пользователя отдельно открыты пять гостевых
  сценариев `/demo/wi/examples/{scenario}`. Они не читают аккаунты, импорты,
  загруженные PDF или редактируемый каталог. Результаты и расписание искусственные,
  учебные определения из кода. Загрузки и ссылки на защищённые PDF отсутствуют;
  личные API не стали публичными. Действия в примере хранятся только в отдельном
  пространстве localStorage. Это публичная демонстрация, не сетевое ограничение.
- Фиксируется время подтверждения; оно включается в личный экспорт и удаляется
  с аккаунтом. Проверка почты не подтверждает текущий статус студента/сотрудника
  навсегда и не заменяет SSO/MFA.

## Настройка на сервере

1. Выбрать согласованный почтовый сервис/SMTP, имеющий право отправлять от
   отдельного адреса проекта. Пароль университетского аккаунта посетителя
   приложению не нужен. В интерфейсе предлагается отдельный пароль приложения.
2. В локальном, некоммитимом `.env` заполнить:
   - `SMTP_HOST`, `SMTP_PORT`;
   - `SMTP_SECURITY=starttls` (обычно 587) или `ssl` (обычно 465);
   - `SMTP_USER` и `SMTP_PASSWORD`, если провайдер требует аутентификацию;
   - `SMTP_FROM` — разрешённый провайдером адрес отправителя;
   - `PRIVACY_MAIL_PROVIDER`, `PRIVACY_MAIL_RETENTION` — настоящий провайдер,
     регион обработки, получатели/субобработчики и сроки хранения писем/логов.
3. Для локального подключения реального SMTP включить
   `REQUIRE_INSTITUTIONAL_EMAIL=true`. В `APP_ENV=production` проверка обязательна
   даже при false; запуск требует заполненного SMTP, HTTPS, Secure-cookie и
   проверенной конфигурации конфиденциальности. `ADMIN_EMAIL` может быть отдельной
   личной почтой оператора: исключение действует только для явно назначенного
   администратора, не для регистрации учебных аккаунтов.
4. Пересоздать контейнеры. Проверить доставку в реальный разрешённый ящик,
   одноразовость, срок действия, недопуск без кода и ошибку внешнего домена.
   По требованиям провайдера настроить SPF/DKIM/DMARC и проверить спам-фильтр.
   Для текущего VPS проверен STARTTLS на порту 2525 и получение теста в спаме;
   остальные ограничения и повторные проверки описаны в «Состояние сейчас».

Первоначальная обработка демонстрационных аккаунтов не является миграцией
реальных университетских личностей. Не переносить реальные пользовательские
оценки из локальной демонстрации в публичную тестовую базу без отдельного решения.

## Дополнительные меры для согласования эксплуатации

### Восстановление пароля — 23.11.2026

На странице входа доступно «Passwort vergessen?». Пользователь указывает почту,
получает код и вводит его вместе с новым паролем (12–200 символов, повторный ввод
проверяется интерфейсом). После смены возвращается к обычному входу; автоматической
сессии нет. Доступны существующие разрешённые учебные аккаунты, в том числе ещё
не подтвердившие почту, и явно назначенные администраторы. Роли, оценки, связи с
импортами и согласие не меняются. Подтверждение кода одновременно доказывает
доступ к почтовому ящику. На почту отправляется также уведомление о смене без пароля.

API: `POST /auth/password/reset/request` с `email`, затем
`POST /auth/password/reset/confirm` с `ticket`, `code`, `new_password`.
Ответ на запрос одинаков для существующих и неизвестных/недопущенных адресов;
SMTP выполняется после ответа в фоне, письма идут только на существующие разрешённые
аккаунты. Если SMTP глобально не настроен, возвращается 503 для любого адреса.
Сбой реальной отправки записывается обезличенно в журнал: пароль не меняется,
новую попытку можно запросить через минуту. Фоновая отправка не является постоянной
очередью: после перезапуска при неполучении письма следует запросить новый код.

Код на 10 минут, максимум 5 неверных вводов; случайный секрет окна и код хранятся
только как хеши в отдельной таблице `password_resets`. Код подтверждения регистрации
не подходит для сброса и наоборот. Для неизвестных адресов сохраняется только
хеш адреса и временные проверочные значения, аккаунт не создаётся. Новый запрос
заменяет прежний код восстановления, но не блокирует действующий вход. Ограничения:
10 запросов с IP за 15 минут, 5 писем на адрес в час и 30 отправок в минуту для
приложения совместно с подтверждением регистрации; ввод кода также ограничен.

Успешная смена атомарно использует код, отзывает прежние сессии, коды подтверждения
и восстановления. Изменение пароля другим способом или отзыв роли аннулируют
восстановление. Удаление аккаунта убирает связанные записи; просроченные записи
очищаются при новых запросах и ежедневном обслуживании. Пароли и коды не пишутся
в HTTP-ответы, журнал или хранилище браузера. Новый код следует вводить в том же
окне, где он запрошен. Восстановление не требует изменения `.env` или нового SMTP.
Новая таблица создаётся при запуске обновлённого backend без удаления прежних данных.

Принципы: [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

### Загрузка PDF и текущий личный отчёт — 23.11.2026

Для аккаунта без актуального согласия выбор PDF открывает модальное подтверждение
Datenschutz по центру экрана. Файл до согласия остаётся только в памяти браузера;
после успешного подтверждения выбранный файл отправляется автоматически. Отмена
окна не отправляет PDF. Серверная проверка согласия остаётся обязательной; при 428
интерфейс предлагает то же подтверждение и повторяет выбранную загрузку.

Личный кабинет автоматически открывает последний успешный импорт. Сохранённый
ранее выбор старого отчёта больше не используется. В шапке указаны имя и дата/время
загрузки PDF в часовом поясе Europe/Berlin; это не дата получения оценок и не дата
формирования документа. Старые структурированные отчёты доступны для экспорта и
удаления в «Datenschutz & Daten», без переключателя в основном дашборде.
Пять сценариев гостевой демонстрации по-прежнему переключаются независимо.

`/imports` возвращает `uploaded_at` и сортирует отчёты по последней успешной загрузке,
затем по ID. Повторная загрузка уже известного PDF обновляет время загрузки и делает
именно его текущим, сохраняя первоначальную `created_at` и не создавая дубля.
Невалидный PDF текущий отчёт не меняет. Для старых записей используется `created_at`.
Nullable-колонка `imports.last_uploaded_at` добавляется при старте без удаления данных.

### Подключение и проверка почтового сервиса

Собственный почтовый сервер не требуется. Можно использовать разрешённый SMTP
собственного почтового ящика либо внешний сервис транзакционных писем.
Подготовка аккаунта Brevo, отправителя и серверная доставка проверены, как
указано в разделе «Состояние сейчас»; попадание во входящие ещё не подтверждено.

### Назначение администраторов

`ADMIN_EMAIL` / `ADMIN_PASSWORD` создают отдельного начального администратора.
Совпадение с существующим учебным аккаунтом не повышает роль автоматически:
запуск приложения продолжается, а оператор получает диагностическое сообщение.
Для осознанного переиспользования выбранного аккаунта есть отдельная команда:

```sh
docker compose run --rm --no-deps backend python -m app.operations provision-admin --email owner@example.test --adopt-existing --reset-password
```

Заменить адрес на точное `ADMIN_EMAIL`. Команда меняет только выбранный аккаунт,
сохраняет его учебные данные, устанавливает пароль из приватного `ADMIN_PASSWORD`,
отзывает сессии/коды и требует нового подтверждения почты. Без `--reset-password`
пароль уже существующего администратора не меняется; без `--adopt-existing`
учебный аккаунт не преобразуется. `check` и `smtp-test` по-прежнему не открывают БД.

Сотрудник сначала регистрируется с `@oth-regensburg.de` и подтверждает адрес.
Затем оператор явно назначает роль через SSH, не передавая пароль сотрудника:

```sh
docker compose run --rm --no-deps backend python -m app.operations grant-admin --email staff@oth-regensburg.de
docker compose run --rm --no-deps backend python -m app.operations revoke-admin --email staff@oth-regensburg.de
```

Это примеры с заменяемыми адресами, выполнять только нужную команду. Назначение
отклоняет `@st.oth-regensburg.de`, чужие домены и неподтверждённые аккаунты.
При смене роли прежние сессии и коды отзываются; пароль сотрудника сохраняется.
Снять роль у `ADMIN_EMAIL` можно после изменения этой настройки, чтобы bootstrap
не назначил её заново. Веб-эндпоинтов управления ролями и переключения режимов нет.

Например, для Brevo официальные параметры — `smtp-relay.brevo.com`, отдельный
SMTP login и SMTP key (не API key). На текущем VPS используется
`SMTP_PORT=2525`, `SMTP_SECURITY=starttls`; порты 465 и 587 дали тайм-аут. До выбора
провайдера проверить договор обработки, фактические места обработки и сроки
логов/содержимого. Не добавлять студентов в маркетинговые списки: код отправляет
только транзакционные сообщения и не передаёт оценки.

[Официальная настройка Brevo SMTP](https://help.brevo.com/hc/en-us/articles/7924908994450-Send-transactional-emails-using-Brevo-SMTP).

Внести `SMTP_*` только в серверный `.env`, защитить файл правами доступа и не
коммитить. В панели провайдера подтвердить адрес отправителя и установить
показанные им DNS-записи; не копировать произвольные SPF-записи из примеров.
Проверить SPF/DKIM/DMARC по результатам полученного письма. На netcup проверить
исходящее SMTP-соединение и правило `netcup Mail block`, не отключая firewall целиком.

После сборки актуальной версии:

```sh
docker compose run --rm --no-deps backend python -m app.operations check
docker compose run --rm --no-deps backend python -m app.operations smtp-test --to your-address@st.oth-regensburg.de
```

Вторую команду запускать только для собственного разрешённого адреса. Она явно
отправляет одно техническое письмо без создания аккаунта и без оценок. Первая
команда не открывает БД, не посылает письма и не печатает SMTP-секреты. Принятие
письма SMTP-сервером не доказывает доставку: проверить входящие и спам, затем
новую регистрацию с вводом кода, неверный код, повторное применение и вход после
подтверждения. Оба домена OTH необходимо проверить реальными доступными ящиками.

### Проверка сервера

- Если выбирается защищённый режим: ограничение на уровне сети/reverse proxy
  по согласованным сетям OTH/VPN, с закрытием альтернативных адресов доступа.
  Списки сетей и параметры маршрутизации нужно получить у ITZ, не выводить их
  из доменного имени или непроверенных заголовков клиента.
- Для публичного режима: уточнить требования независимого внешнего аудита,
  ответственного за обновления и реагирование, мониторинг без кодов/оценок в
  журналах, резервирование и проверку восстановления. HTTPS и ограничения
  приложения обязательны, но недостаточны для заявления о соответствии письму.
- Для администрирования рассмотреть согласованное SSO/MFA на входном шлюзе.
  Наличие Microsoft у студентов само по себе не даёт прав подключить вузовский
  tenant; параметры и разрешение должен предоставить ответственный OTH.
