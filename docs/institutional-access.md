## Граница решения

Проверка почты контролирует, кто получает аккаунт и доступ к API, но не закрывает
сам вебсервер от интернета. Домен сайта, суффикс email и сеть OTH — три разных
вещи. Наличие адреса @oth-regensburg.de не делает запрос пришедшим из Hochschulnetz.

По предоставленному письму возможны публичный доступ с требуемым независимым
аудитом либо сетевое ограничение; отдельно описывается возможность внешнего
хостинга с сохранением требований к конкретному сервису. Нельзя самостоятельно
считать внешнего провайдера, WAF или верификацию email заменой согласования и
аудита. Применимость и режим для этого проекта нужно уточнить у руководителя,
ITZ и Informationssicherheitsbeauftragter. Автоматические тесты разработчика
не являются независимым внешним аудитом.

не увидел принципиальной проблемы в собственной регистрации либо проверке

сервера или подтверждение соответствия опубликованной конфигурации. Требования
к возможной передаче факультету отдельно не согласованы.

## Что реализовано

- Допускаются ровно `st.oth-regensburg.de` и `oth-regensburg.de`; похожий суффикс,
  дополнительный поддомен и чужой домен не принимаются. Это не механизм
  назначения ролей: зарегистрированный сотрудник получает обычный личный доступ.
- Для ограниченного режима после регистрации приходит шестизначный код на 10
  минут. Нужны и код, и случайный секрет текущего окна подтверждения. В БД
  сохраняются хеши; открытые коды/секреты не попадают в ответы API или логи.
- Новый аккаунт создаётся после подтверждения. До этого временно хранятся
  pending-регистрация с хешем пароля и согласие; неподтверждённый адрес нельзя
  заранее занять как действующий аккаунт. Просроченные записи удаляются при
  последующих запросах и ежедневной очистке.
- Максимум 5 ошибочных попыток для одного кода. Повторная отправка — не раньше
  60 секунд, максимум 5 отправок на адрес за час и 30 на приложение за минуту.
  Новый код отменяет предыдущий, успешное подтверждение одноразовое и атомарное.
- Старые аккаунты не считаются подтверждёнными автоматически. При включении
  режима старая сессия без подтверждения больше не даёт доступ к данным.
  После подтверждения вход осуществляется отдельным паролем приложения.
- В ограниченном режиме личные обзоры, прежние диагностические примеры и PDF
  каталога требуют входа. Сведения о конфиденциальности, вход и health доступны.
- Обновление 21.11.2026: по запросу пользователя отдельно открыты пять гостевых
  сценариев `/demo/wi/examples/{scenario}`. Они не читают аккаунты, импорты,
  загруженные PDF или редактируемый каталог. Результаты и расписание искусственные,
  учебные определения из кода. Загрузки и ссылки на защищённые PDF отсутствуют;
  личные API не стали публичными. Действия в примере хранятся только в отдельном
  пространстве localStorage. Это публичная демонстрация, не сетевое ограничение.
- Фиксируется время подтверждения; оно включается в личный экспорт и удаляется
  с аккаунтом. Проверка почты не подтверждает текущий статус студента/сотрудника
  навсегда и не заменяет SSO/MFA.

## Настройка на сервере

1. Выбрать согласованный почтовый сервис/SMTP, имеющий право отправлять от
   отдельного адреса проекта. Пароль университетского аккаунта посетителя
   приложению не нужен. В интерфейсе предлагается отдельный пароль приложения.
2. В локальном, некоммитимом `.env` заполнить:
   - `SMTP_HOST`, `SMTP_PORT`;
   - `SMTP_SECURITY=starttls` (обычно 587) или `ssl` (обычно 465);
   - `SMTP_USER` и `SMTP_PASSWORD`, если провайдер требует аутентификацию;
   - `SMTP_FROM` — разрешённый провайдером адрес отправителя;
   - `PRIVACY_MAIL_PROVIDER`, `PRIVACY_MAIL_RETENTION` — настоящий провайдер,
     регион обработки, получатели/субобработчики и сроки хранения писем/логов.
3. Для локального подключения реального SMTP включить
   `REQUIRE_INSTITUTIONAL_EMAIL=true`. В `APP_ENV=production` проверка обязательна
   даже при false; запуск требует заполненного SMTP, HTTPS, Secure-cookie и
   проверенной конфигурации конфиденциальности. `ADMIN_EMAIL` тоже должен быть
   университетским, если задан. Админ создаётся только явной конфигурацией.
4. Пересоздать контейнеры. Проверить доставку в реальный разрешённый ящик,
   одноразовость, срок действия, недопуск без кода и ошибку внешнего домена.
   По требованиям провайдера настроить SPF/DKIM/DMARC и проверить спам-фильтр.
   Реальная доставляемость, ограничения исходящего SMTP и доступность ящиков
   остаются непроверенными до выбора хостинга и почтового сервиса.

Первоначальная обработка демонстрационных аккаунтов не является миграцией
реальных университетских личностей. Не переносить реальные пользовательские
оценки из локальной демонстрации в публичную тестовую базу без отдельного решения.

## Дополнительные меры для согласования эксплуатации

### Подключение и проверка почтового сервиса

Собственный почтовый сервер не требуется. Можно использовать разрешённый SMTP
собственного почтового ящика либо внешний сервис транзакционных писем.
Подготовка аккаунта Brevo и отправителя выполнена, как указано в разделе
«Состояние сейчас»; серверное подключение и реальная доставка не проверены.

Например, для Brevo официальные параметры — `smtp-relay.brevo.com`, отдельный
SMTP login и SMTP key (не API key). Наше подключение можно настроить на
`SMTP_PORT=465`, `SMTP_SECURITY=ssl`; 587 допустим только с STARTTLS. До выбора
провайдера проверить договор обработки, фактические места обработки и сроки
логов/содержимого. Не добавлять студентов в маркетинговые списки: код отправляет
только транзакционные сообщения и не передаёт оценки.

[Официальная настройка Brevo SMTP](https://help.brevo.com/hc/en-us/articles/7924908994450-Send-transactional-emails-using-Brevo-SMTP).

Внести `SMTP_*` только в серверный `.env`, защитить файл правами доступа и не
коммитить. В панели провайдера подтвердить адрес отправителя и установить
показанные им DNS-записи; не копировать произвольные SPF-записи из примеров.
Проверить SPF/DKIM/DMARC по результатам полученного письма. На netcup проверить
исходящее SMTP-соединение и правило `netcup Mail block`, не отключая firewall целиком.

После сборки актуальной версии:

```sh
docker compose run --rm --no-deps backend python -m app.operations check
docker compose run --rm --no-deps backend python -m app.operations smtp-test --to your-address@st.oth-regensburg.de
```

Вторую команду запускать только для собственного разрешённого адреса. Она явно
отправляет одно техническое письмо без создания аккаунта и без оценок. Первая
команда не открывает БД, не посылает письма и не печатает SMTP-секреты. Принятие
письма SMTP-сервером не доказывает доставку: проверить входящие и спам, затем
новую регистрацию с вводом кода, неверный код, повторное применение и вход после
подтверждения. Оба домена OTH необходимо проверить реальными доступными ящиками.

### Проверка сервера

- Если выбирается защищённый режим: ограничение на уровне сети/reverse proxy
  по согласованным сетям OTH/VPN, с закрытием альтернативных адресов доступа.
  Списки сетей и параметры маршрутизации нужно получить у ITZ, не выводить их
  из доменного имени или непроверенных заголовков клиента.
- Для публичного режима: уточнить требования независимого внешнего аудита,
  ответственного за обновления и реагирование, мониторинг без кодов/оценок в
  журналах, резервирование и проверку восстановления. HTTPS и ограничения
  приложения обязательны, но недостаточны для заявления о соответствии письму.
- Для администрирования рассмотреть согласованное SSO/MFA на входном шлюзе.
  Наличие Microsoft у студентов само по себе не даёт прав подключить вузовский
  tenant; параметры и разрешение должен предоставить ответственный OTH.

Основания для технической проверки:
[OWASP Email Validation and Verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html),
[OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
